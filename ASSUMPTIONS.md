# Assumptions and design decisions

- A shift is a separate class with its own capacity, for example `Class 6 - Morning Shift`. There is no separate shift entity, seat selection, class editing or class deletion in the required API.
- Student identity is the supplied `X-Student-Id`, exactly 17 ASCII digits, kept as text to preserve leading zeros. The assignment explicitly omits login. This header is not authentication; someone who knows an ID can supply it. Class creation is likewise not protected by a real admin role.
- The frontend uses English labels and date formatting; the brief does not mandate Bengali UI. The selected student ID is remembered in `localStorage` so it survives both page reloads and closing/reopening the browser. Explicitly applying a different ID resets student views; late requests cannot repopulate them. If storage is unavailable or cleared, re-enter the same ID to recover applications from the server. No admission state is stored locally. The duplicate-admission restriction is per class: a student may apply to different classes/shifts.
- Confirmation simulates successful fee payment. No money, payment provider or fee amount is involved. Repeated confirmation/cancellation by the owner returns success. Confirmed admissions cannot be cancelled; expired/cancelled holds cannot be confirmed. A new hold may be created after cancellation or expiry.
- A confirmed admission continues occupying its seat after its original hold deadline. A HELD row with a deadline at or before database time is effectively expired, even if the worker has not yet persisted EXPIRED. History is retained; cancellation does not delete records.
- PostgreSQL `clock_timestamp()` is the authoritative business clock. Hold duration defaults to 600 seconds and must be positive. The browser countdown estimates remaining time using `expiresAt` and the device clock; backend responses decide the state. Visible views refresh every five seconds and on focus, and countdown zero triggers a refresh. Browser clock skew cannot allocate or confirm an expired seat.

## Concurrency, including the two-process bonus

All capacity-changing operations (create, confirm, cancel and expiry) lock the same class row before changing holds. A Read Committed transaction keeps that PostgreSQL `FOR UPDATE` lock until commit. Creation expires stale holds, checks duplicate active admission and capacity, inserts the hold, then commits. Another request for that class waits and checks the committed result; other classes use different locks. A partial unique index on `(StudentId, ClassId)` additionally prevents multiple HELD/CONFIRMED rows for the same student and class. The unique index alone does not enforce capacity.

Coordination happens in PostgreSQL, not a process-local C# lock. `docker-compose.test.yml` runs two independent APIs on container ports 8080 and 8081 against one temporary database. An automated test sends 60 allocations across both processes to a seven-seat class with one already-confirmed admission: six succeed, the rest conflict, and both APIs/database report six held plus one confirmed. Another test splits 30 requests for one student across both APIs and verifies only one hold exists.

Workers select up to 100 available class rows with `FOR UPDATE SKIP LOCKED`, then expire due holds in one transaction. Selection and locking are in the same query, so 100 busy classes cannot hide an unlocked later candidate. Both instances may run workers safely. This does not guarantee strict network-arrival FIFO: PostgreSQL lock acquisition orders competing writes, and a hot class serializes them. Direct SQL writers must follow the same locking protocol. These tests are not a production throughput benchmark.

## Scope and delivery choices

- One API project uses controller/service/repository folders. Services use the shared scoped `AppDbContext` for transactions and SaveChanges; this is a small-project unit-of-work choice, not strict persistence-independent Clean Architecture. LINQ handles ordinary queries; parameterized SQL handles PostgreSQL locks and clock reads.
- React uses local state, a small identity context and shared fetch hooks. Unknown write outcomes are not automatically retried; users check application history. Server responses are authoritative, including conflicts and ownership errors.
- The frontend's `/api` requests pass through its web server. `API_BASE_URL` changes that server's backend target at container startup, without rebuilding JavaScript or requiring CORS. The API remains directly available at localhost:8080. Startup applies migrations; a production deployment would normally manage migrations/secrets separately.
- No initial classes/admissions are seeded. Create classes through the UI. The named PostgreSQL volume persists across ordinary restarts; test stacks use separate temporary databases. `/health` is host liveness, not a comprehensive database readiness check.
- Frontend behaviour tests intercept API responses for deterministic edge cases. Separate browser journey tests use the actual Docker frontend, API and PostgreSQL, with a 12-second hold duration for fast expiry checks. Backend integration tests retain the normal 600-second default.
